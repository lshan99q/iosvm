## 零、一句话现状

1. **启动稳了**：三族 deadline（ticket / `lock_panic_timeout` / waitq）都抬到 60 s 后，
   8 次冷启动 **8/8 到界面、0 panic**（第九阶段 P0''）。
2. **停顿还在、原因未知**：每次启动 24–44 次 >1 s 的空洞，最长 14.68 s；宿主 I/O 与 `ZERO_RAM` 重写都已排除
   （第八阶段四次对照：停顿窗内 I/O 压力比窗外低），panic 栈落在调度器的 timeshare 维护路径上。
3. **画面卡在「记录器能到的那一层」**：B 路（`spec.def` 之外的 EGL 槽位）已否定——12 个候选在 UI 起来时 0 调用；
   W2 仍不成立。P3' 的四配置表被停顿吞掉（最好的格 20 秒窗口只有 2 帧）。

所以这一阶段只做三件事：**把停顿的栈抓出来**、**把测量口径从「固定 20 秒」改成「停顿之外」**、
**给 B 路定下一个靶子**。

## 三、需求详述

### P0''' 停顿的栈（半天）

工具已经在核心里：`osfmk/arm64/user_exception_trace.c`

```
ustacks=NAME          哪个进程的线程（"top" = 谁在跑；别的名字 = 该进程的线程在等什么）
ustacks_at=SECONDS    启动后多久开始
ustacks_ms=MILLISECONDS  采样周期
ustacks_count=N       采 N 次就停（0 = 一直）
ustacks_tname=TEXT    只采线程名含 TEXT 的（"coreanimation" = 窗口服务器的渲染线程；"*" = 全部，并写进 loader 日志）
```

两次启动（同一镜像 `/tmp/root-fixed-net.apfs`、同一参数）：

1. `XCMD="slto_us=30000000 tlto_us=60000000 lpto_us=60000000 ustacks=top ustacks_at=420 ustacks_ms=1000 ustacks_count=600"`
   —— 看**停顿窗口里谁在跑**（若一个都没有，说明整机被某个自旋/中断占住）；
2. `XCMD="… ustacks=WindowServer ustacks_tname=* ustacks_at=420 ustacks_ms=1000 ustacks_count=600"`
   （进程名以 `ps`/日志里的实际名字为准）—— 看**停顿窗口里渲染线程在等什么**。

符号化：`qemu/symstack.py`（宿主侧把地址翻成符号）。判据：≥5 个 >2 s 的窗口、每窗口 ≥2 个采样，
并把窗口内的栈与「非窗口时段」的栈对比——**不同**才有归因。

### P1''' 停顿的可复现缩小（1 天）

按 P0''' 的结果二选一：
- 指向某个锁/驱动：替换或绕开（例：若指向 `vfs`/`vm` 的锁，试 `ZERO_RAM=0` + `drop_caches` 的组合，看停顿数）；
- 指向「整机没有线程在跑」：查宿主侧 QEMU 是否停住（`gdb -p` 采一次 QEMU 的线程栈；或 `perf top` 看 TCG 线程）。

判据：停顿数下降 ≥50%，且启动仍 8/10 以上到界面。

### P2''' 测量口径（半天）

`harness/drive-scroll.sh` 已有「窗口内 guest 侧帧数」；本阶段加一个 `WINDOW_FRAMES=N` 模式：
**从第 N 帧到第 N+120 帧**为窗口（而不是固定 20 秒），这样停顿被排除在窗口之外，四配置可比。
四格各跑一次（同 P3' 的镜像），表里给「120 帧用了多少秒」→ fps。

### P3''' B 路的靶子（读代码，不占 VM）

在 `iosvm-work/hakios-xnu-kernel` 与已知的 CA 符号里找：
- CA 的渲染路径（`CA::Render::…`、`QuartzCore`、`SkyLight`/`backboardd`）上，**文字/图标的层内容从哪来**；
- 它是否经过 `IOSurface`（若是，`glslots` 的 `none into an IOSurface that is known here` 就是线索）；
- 给一句「下一步接哪一段」——不承诺实现。

## 四、不做（已被数据否掉，别重试）

- 不再单独抬一族 deadline（第八阶段：修 ticket，spinlock/waitq 接着炸；第九阶段：三族一起抬已 8/8）。
- 不再在 EGL 表里找 glyph（第九阶段：12 个候选 0 调用）。
- 不再用固定 20 秒窗口测帧率（第九阶段：窗口落进停顿，最好的格 2 帧）。
- 不再用哈希比 panel/picture（85.35% 是上限而不是错误）。
- 不在停顿未归因前声称「稳定 9 fps」。
- 像素去重、客户机内 GL 加速、只降分辨率、`touch.py stacks`、`pkill -f`、并行第二台虚拟机。

## 七、诚实的预期

- **能确定的**：`ustacks` 在这个端口是现成的（`user_exception_trace.c` 里那套 boot arg 与 `symstack.py` 都在），
  两次启动就能拿到窗口内的栈；改测量口径是一天的活。
- **不确定的**：停顿的归因。它可能指向调度器（panic 栈的样子）、也可能指向 `vfs`/`IOMobileFramebuffer`
  的锁；如果两次采样都「没有线程在跑」，那就得去 QEMU 侧看 TCG 线程——那是另一门手艺。
- **不能承诺的**：B 路一定能接进流里；以及「稳定 9 fps」。
