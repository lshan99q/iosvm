# 画面缺陷：黑块闪烁 / 文字虚线 / 应用突然变大（2026-11-20）

来源：主人看 `s28-ux9`、`s28-ux11` 录像后报的问题。三个现象都不是“卡顿”，是**回放合成**的问题。

## 一、黑块闪烁（时钟秒针位置闪黑）、大面积黑块
- 现象：时钟秒针、图标、文字下方在刷新位置出现黑块；滑动/启动过渡时出现大片黑区。
- 根因（已知）：我们的远程路径是**脏矩形回放**——guest 每帧 `glClear` 整个 drawable，然后只重画变化区域；
  真实设备上“没重画的地方保持上一帧”，但**宿主回放会把 clear 照做**，于是宿主 framebuffer 被清空、未重画区域变黑。
  静态补丁只是把“静止主屏”的下半屏补回去（`GLWIRE_PATCH_MIN_COVERAGE`），一旦画面活跃（覆盖率高于阈值）就不贴，
  黑块立刻露出来。这解释了“时钟位置闪黑”和“大面积黑块”。
- 修复方向（已实现，待验证）：宿主侧加 `GLWIRE_SKIP_CLEAR=1`——**不重放颜色 clear**，让帧累积在上一帧之上，
  与真实显示器行为一致。代码：`tools/glwire/dispatch.inc` 的 glClear 分支 + `host_glwire.c` 的 `host_skip_clear`。
- 验收：同一操作序列（`rc.ux` 三轮 burst）下录像里不再出现黑色空洞；静止时画面不被清空；必要时再把 `PATCH_COV` 调低。
- 风险：如果某帧本该清成黑色（例如切到深色背景的应用），会残留旧内容 → 需要给“整屏清为纯色”的情况留例外（第二条）。

## 二、文字下方的虚线（下划线）
- 现象：图标名的下划线是虚线/断点，不是实线。
- 现状：属于“文字渲染保真度”类问题，一直在判死清单里（`文字虚线`），原因是字形/下划线栅格化路径（glyph 采样、atlas 上传）；
  它与帧率无关，纯观感问题。
- 安排：排在黑块修复之后（本周内给一次专项定位：抓一条带下划线的 `glDrawElements`/atlas 记录，和真实 iOS 对比像素）。
  若定位成本高，则在需求文档里交给外部（Claude）处理。

## 三、News 应用“突然变大”
- 现象：某一阶段 News 的图标/内容被放大（见主人截图）。
- 待查：疑似应用窗口的 **scale/transform** 状态在回放里没有被重置（上一个应用的 viewport/变换残留），
  或 launch 动画结束时没有收到“恢复”序列。需要一次带 News 的复现（打开 News → 截图 → 与真机比例对比）。
- 计划：复现一次并抓该帧的 record 流（`GLWIRE_DUMP_FRAME`），比对 transform 调用。

## 五、2026-11-21 00:30 新证据：label FBO 里是**实线**，屏幕上是虚线
同一次运行（`p1-fix2`，`GLWIRE_LABEL_DUMP=1`）dump 出的 label FBO（750×200）：
- 文字占 rows 0–60；
- **rows 61–63 是一条 x=24..125 的连续实线**（102 px 宽、3 px 高，见 `1-label-2-fbo-5-750x200.bgra`）。

也就是说：**guest 渲染 label 时画的是一条实线下划线**（不是虚线），而最终屏幕上看到的是虚线。
→ 虚线是在 **label FBO → 屏幕** 这一步被引入的（缩放/采样：750 与 1125 之间的非整数比例 + NEAREST 采样，
   3 px 的实线被 2/3 或 1.5 倍采样打散成 2–3 px 的点），而不是字形或 tile 内容本身。

下一步（一次运行即可定论）：
1. 用 `GLWIRE_SAVE=<dir>` 或让 label FBO dump 与 `GLWIRE_DUMP_AT` 在**同一帧**触发；
2. 把屏幕上的带与同帧 FBO 的实线逐像素对齐（缩放矩阵可反推）；
3. 若确认是采样，修法二选一：① 该 pass 改 `GL_LINEAR`；② 直接让 guest 不画这条下划线（如果它本就不该存在）。

## 六、2026-11-21 02:30 决定性对照：**原生 3x 渲染时没有这条线**
- 用 `fbscale=3` 跑一发（`p1-scale3`，display 1125×2436 = panel 1125×2436，1:1 无缩放）：
  guest 起机正常，主屏标签（Health / Wallet / Settings / TV / Podcasts / App Store / Maps）**完全没有任何下划线/虚线**，字也干净。
- 而 `fbscale=2`（display 750×1624，内部 2x 渲染）时，同一批标签下面出现 1–2 px 的虚线段。
- 结合上一节（label FBO 里是**3 px 实线**）：这条“下划线”是 **2x 渲染路径的产物**——可能是文本渲染时多画了一条被压扁到 1–2 px 的副本（内容像被横向压扁的字形片段），
  在 3x 路径里根本不画。
- 结论：**它不该存在**（真机/3x 都没有）。因此修法优先“**在 2x 路径上不画/清掉这条带**”，而不是“把虚线补成实线”。

  用“短段数 ≥4 且填充率 0.2–0.85”可以把它和文字行区分开（文字行的段更长、且上方有字身）。
- 下一步：在 host 的 label pass（scissor 切换到标签区域时）读回该区域、按上面的形态擦掉这条带（或直接在 guest 侧 2x 路径跳过这次绘制），再跑一发验证。

## 八、2026-11-21 06:10：找到 label pass 的可识别特征，修复应放在这里
- 参考物：**静态补丁图 `/tmp/patch-full.bgra`（正确的主屏）里没有任何 dash-like 行**（用“runs 3–12、span 40–300、fill 0.3–0.8”筛，结果为 0）；
  同一滤镜在实时帧里会命中 51 行（含图标行），所以**在整幅画面上做启发式修复会误伤**，不能那么做。
- 但 label pass 在 host 的 draw 日志里可识别：例如
  `fbo 13 viewport 0,0 138x138 scissor on 0,0 120x20 … count 54 program 35`——**小 scissor（120x20）+ 很多顶点（27 个 quad）** 就是一次文字行绘制。
- 因此修复应当放在**这个 pass 结束时**（host 已知 scissor 与 FBO）：
  1. 读回该 scissor 区域；
  2. 在区域底部找“与文字分离的 1–2 行短段”（这里没有图标干扰，判据可靠）；
  3. 用背景色清掉这几行（或整行清成透明），再继续合成。
- 这比“整幅图启发式修复”安全得多，也比 guest 侧按固定行号 scrub（会切断笔画）精确。
- 下一步：在 host 的 draw 路径里，跟踪 scissor 变化 → pass 结束时做上面的 readback/clear；接一个 `GLWIRE_LABEL_SCRUB=1` 开关，跑一发带录屏验证。

## 九、2026-11-21 10:30 验证结果（`fix-valid1`，录像 34,516 帧 / 149 MB）
1. **黑块**：`SKIP_CLEAR=1`（不重放颜色 clear、帧累积）后，起机后的主屏画面**完整、没有黑色空洞**（图见录像 33 分钟处）——
   但代价是**重影**：同一标签出现两份（如 Health / Settings 各叠了 1–2 px 的第二份）。原因是不 clear 时旧内容留在画面上，
   而 guest 的脏矩形没有覆盖“旧文字”的位置。
2. **开机绿块**：仍在（起机前 10 秒，右下角一整块 (0,241,0)）。宿主侧“建 framebuffer 先清黑”没有解决 → 绿色不是宿主未初始化内存，
   而是**被当作画面发布的内容**（Apple logo 与绿块同帧出现）。
3. 结论（重要）：**2x 路径的脏矩形/缩放覆盖不足**是共同根因——黑块（clear 之后没重画）、重影（旧内容没被覆盖）、
   文字下方虚线（文字行的脏矩形差 1–2 px）都在 3x（1:1）路径下消失。绿块另查（可能是 payload 的显示初始化）。
- 下一步：
  ① 找 payload（`qemu/payload.bin`，源码不在内核树里）里 `fbscale` 的实现，确认 2x 时 CA 的脏矩形坐标空间；
  ② 若脏矩形按 panel(1125) 计算而表面是 750，则在驱动侧把脏矩形**向外取整**（floor/ceil）并加 1 px 余量，三处症状应一起消失；
  ③ 绿块单独查 payload 的显示初始化（是否有一段默认填充色）。

## 十、2026-11-21 16:00 2x vs 3x 同活动对照（主机 load ≈0.9，脚本相同）
| 项 | 2x（750×1624，`scale2-ux`） | 3x（1125×2436，`scale3-ux`） |
|---|---|---|
| 起机 | 12.3 min（14:03:35→14:15:52） | 12.9 min（12:05:21→12:18:12） |
| 45 min 全段 | 10,475 帧 / 3.85 fps / 210 ms 帧 | 20,650 帧 / 7.72 fps / 99 ms 帧 |
| 起机后 33 min | 10,273 帧 / **5.20 fps** / **154 ms** | 10,464 帧 / **10.53 fps** / **71 ms** |
| 画面瑕疵 | 虚线、黑块、重影（活动时） | 全部没有 |

**结论（反直觉但成立）**：3x 不但画面正确，**guest 侧每帧还更便宜**。原因在 `MiniIOMobileFramebuffer.cpp`：
`job->unscaled` 只有在「层与 panel 同尺寸」时成立（3x 成立）→ 走 memcpy 快路径；2x 每次 swap 都走逐像素
nearest 缩放（`drawRows` 的 scale 分支，2.7M 像素/帧）→ 更贵。

**待确认**：① 上面的平均含静止段，需固定动画做严格 A/B；② 3x 的宿主回放成本是 2.4 倍像素，尚未单独测；
③ 3x 录像器已修（H.264 需偶数宽高，1125→1124 裁切）。

## 十一、2026-11-21 19:10 更正：3x 不是更快，是更慢（上一节的 fps 数字作废）
上一节的 fps 来自 `samples.csv` 里的 guest 帧计数，而串口日志里**同时存在多个独立的帧计数器**（不同 pid/连接各打一份
`hakios-gl: f N`），取样取到哪一条不确定 → 那个对照的数字不可靠。**作废。**

**可靠口径**：录像器按“每次画面发布”计数（`recorded N frames in T s`）：
| 运行 | 窗口 | 捕获画面数 | 平均 |
|---|---|---|---|
| `scale2-ux`（2x，750×1624） | 2700 s | 33,590 | **12.4 fps** |
| `scale3-v2`（3x，1125×2436） | 2700 s（活动） | 12,664 | **约 4.7 fps** |
→ **3x 约慢 2.6 倍**，与像素数 2.4 倍吻合。上一节“3x 更便宜”的结论**撤回**。

**结论修正**：3x 画面干净但代价太大；**交付仍用 2x**，改为定向修 2x 的脏矩形/缩放问题
（`MiniIOMobileFramebuffer.cpp` 的 `drawRows` 缩放分支与 `unscaled` 判定）。
另：录像器新发现一个 bug——未设置 `time_base` 导致 mp4 时长被写成 88,399 s（播放器会跳）；已修（`Fraction(1,1000)`），下次录像生效。
