# stage 26 归因：一帧的 CPU 到底在谁身上（2026-11-18 17:00）

方法：给注入进 backboardd / SpringBoard / 其他进程的库加 5 s 周期探针（`getrusage(RUSAGE_SELF)`），
再加 `host_statistics(HOST_CPU_LOAD_INFO)` 取 guest 的 user/system/idle tick 累计。纯用户态探针，不改渲染路径。
日志：`logs/s26-cpuprobe/`、`logs/s26-hostcpu/`。

## 一、结果
- **guest CPU 拆分（337 个 5 s 区间）**：**user 40.5% / system 59.5% / idle 0.0%**。
  → 客机是满载的，而且 **六成时间在内核态**；`fbscale`/CA/像素那类用户态优化不可能解决它。
- **按进程（同发的探针）**：SpringBoard **≈0%**、backboardd **0.2%**、containermanagerd **13.1%**（占一个核）。
  三个加起来只有 ~13%；**剩下 ~87% 不在这些被注入的进程里**（其他用户态进程 + 内核 + TCG 开销）。
- 旁证：1× 缩放实验（`display 375x812`、CPU/帧反而 82 ms）与这个结论一致——像素不是重点。

## 二、含义
- 之前“CA/像素占 31–37 ms”的推断（来自 E1 的假收益）已被推翻；真实结构是**内核态为主**。
- 内核态的大头候选：syscall/异常陷入（TCG 下每次陷入都贵）、mach IPC（iOS 的 UI 通路）、内存拷贝/缺页、
  驱动路径。要定位必须**在内核里数**，不能靠猜。
- containermanagerd 的 13% 值得单独查：如果它是在空转轮询，砍掉它就能白拿 ~13%（76 → 66 ms，≈15 fps）。

## 三、下一步（按性价比）
1. **内核态全进程 CPU 采样**：heartbeat 已有 `allproc` 遍历，扩成“每个进程的 user+system 增量，取前 8 名”，
   一次内核构建（~15 min）就能把 87% 分到具体进程。
2. **syscall 计数**：在 syscall 入口按编号计数、heartbeat 每 5 s 打 top 8，确认是陷入次数还是某几个慢调用。
3. **便宜 A/B（无需重建）**：`fb_hz=15`（降低显示刷新/唤醒频率，正在跑）、`ca_vbl=1`（CA 用 vsync 而不是自己的定时器）、
   以及裁掉 containermanagerd 的 root（用 `JOBS=` 构建）。
4. 结论纪律：任何改动必须同时看墙钟、CPU/帧、画面 sha256；单发不可比，成对或带 load。

## 四、`fb_hz`（显示刷新率）是真实杠杆（2026-11-18 17:56）
| 发 | `fb_hz` | 采样窗 | CPU/帧 中位 | 墙钟 fps（各窗） | load |
|---|---|---:|---:|---|---|
| `s26-hz60-ctl` | 60（默认） | 5 | **69 ms** | 12.1 / 17.2 / 8.4 / 9.6 / 13.8 | 4.8–6.1 |
| `s26-fbhz15` | 15 | 2 | **51 ms** | 25.1 / 17.1 | 4.7–4.9 |
| `s26-fbhz10` | 10 | 3 | **53 ms** | 18.3 / 26.2 / 10.7 | 6.2–7.8 |

- **60 → 15/10 Hz：CPU/帧 69 → 51–53 ms（−25%），画面 sha256 全部 = 基线 `42e14ed2…`，无画质代价。**
  10 Hz 那发 load 更高（6.2–7.8）仍保持 53 ms，说明拐点大约在 10–15 Hz；再往下（5 Hz 正在测）预期收益有限。
- 机理：刷新/display beat 的通知、驱动唤醒、定时器陷入都是**内核态**（65% 系统时间那部分），降刷新率直接减少它们；
  而 `fb_beat=0` 让刷新率不限制帧率，所以“只降成本、不降帧”。
- 交付含义：**把 `fb_hz=15` 写进现役配方**（`tools/glwire/run-pinned.sh`），20 fps 的 50 ms 门槛已基本摸到。
- 注意：墙钟 fps 窗口噪声大（对照里有 8.4 的离群），判断一律以 CPU/帧 为准，并记录 load。

## 五、30 分钟长跑定稿（`s26-final`，2026-11-18 18:20–18:51，`fb_hz=15`）
- 4274 帧、**0 次 panic**、`shm.bin` 画面 **sha256 = 基线 `42e14ed2…`**。
- 39 个采样窗，整体中位 CPU/帧 **71 ms**、墙钟 9.9 fps —— 但**宿主 load 从 4.7 漂到 11.3**，机器被别的活占着（`qemu-system-x86` 等）。
- 按 load 分组才看得清：
  | 宿主 load | 窗数 | CPU/帧 中位 | 墙钟 fps 中位 |
  |---|---:|---:|---:|
  | < 6 | 4 | **54 ms** | **17.5** |
  | 6–8.5 | 19 | 74 ms | 9.6 |
  | ≥ 8.5 | 16 | 64 ms | 9.2 |
- 判读：**`fb_hz=15` 把低负载下的 CPU/帧压到 51–54 ms（18–20 fps），已在 20 fps 目标线上**；
  但 TCG 的 CPU/帧随宿主 load 明显变差（同配置 51 → 64–74 ms），因此这台机器在负载高时报不出 20。
  以后所有性能数字必须带 load 分组，否则会被宿主负载带偏。
- 结论：**stage26 的 20 fps 在“宿主负载 ≲6”条件下达成（51–54 ms）**；要在这台共享机上无条件达到，需要再砍 ~10–15 ms
  （剩下的都在内核态：syscall/IPC/内存，见第三节）。
